# Security: what could go wrong, and what stops it

The [README](../README.md) has the short version. This is all of it.

WordPress, its plugins and themes, and whatever they write are untrusted. The container can write `wp-content/`,
`var/export` and `var/inbox` and nothing else. Nothing it writes is sourced or followed, and Offprint never runs it by a
lookup of its own: before anything is looked up on the PATH, every Offprint command leaves out of it each entry that is
the site folder or inside it, and each that names no fixed folder (`.`, an empty or a relative entry), saying so, and
each that can't be entered when it starts (the last row below); it keeps each of the rest as the folder it leads to
then, not as its name. The rest of the PATH is yours: a program in an absolute entry outside the site folder runs as
you, as it would for any command you run.

| What could go wrong | What stops it |
| --- | --- |
| WordPress keeps writing the export while it is checked. | Only a private copy, `site.new`, is checked and published. |
| A plugin plants a `.git` folder, or a `.gitattributes` or `.gitmodules` file, to make git run its commands or change how files are stored. | The checks refuse them in the export, and a publish refuses a git repository inside `wp-content`. Git runs with `core.fsmonitor=false` and, where it supports it, takes attributes from the empty tree, not from files on disk. |
| A plugin's own `.gitignore` silently drops files from the published site. | The commit is built from a private index, and the publish refuses if anything would be left out (WordPress's cache and upgrade folders and `debug.log` excepted). |
| WordPress changes Offprint's plugin, which it runs from its copy in `wp-content/mu-plugins/` and can write there, so that a publish commits the change with the rest of `wp-content/`. | A publish refuses uncommitted changes to the copy before the export, and, once the commit is built, refuses unless the plugin in it is exactly this Offprint's own `plugin/`: each file's bytes and executable bit, and no other file. It names the first path that differs and says what to do; nothing is committed. A dry run compares the copy on disk the same way, never through a link. Not stopped: WordPress can still change the copy it runs between publishes, and another plugin in the same PHP process can change what the exporter writes; that is why the checks on the Mac, which read only the private copy, are the gate. |
| A page links to `wp-admin`, `wp-login.php`, XML-RPC or the REST API, or mentions the local hostname. | `bin/check-site` refuses. |
| WordPress writes a file the Mac later reads: a `site.json` in `wp-content`, or a bad publish request. | A `site.json` inside another site folder is refused. A request is moved out first, must be a plain file of at most 1 KB, and only its first 200 bytes are read, as data. |
| The repository holding every upload (and, in commits made before the backup was encrypted, a readable `backup/db.sql`: drafts, password hashes) is public. | `offprint publish` asks `gh` and refuses to push. If `gh` is missing or does not answer, it warns instead. |
| Whoever can read the site's repository reads the database: drafts, password hashes, commenters' email addresses. | The backup is committed only encrypted (`backup/db.sql.age`), to public keys in `site.json`; a publish refuses when there is none, or no `age` to encrypt with. The private key is yours, and Offprint never holds it. `wp-content/` (uploads, themes, plugins) is still committed as it is. |
| What wrangler prints goes to `var/publish.log`, which WordPress can read: the token, should it ever print it; and, when Cloudflare refuses the token for the account, the name and id of every account the token can see (a real account's name held its owner's email address), and, when the token lacks User Details Read, who is logged in. | The adapter's filter replaces the token's value with `[token hidden]`. It leaves out, on every stream, each line that starts (after any spaces) with a box-drawing character of a table (`┌ │ ├ └`) or with 👋, and everything from a line that is exactly "Getting User settings..." to the end of the table that follows it (to the end of that stream when the table never closes). It writes one line in place of what a stream had left out. Nothing else of wrangler's is left out: a line that only holds those words (an uploaded file's name) is kept. |
| Another site or service already uses an address, host name, port, launchd label or Docker compose project. | `host-setup` refuses before changing anything, and every command that runs Docker compose refuses a project that is not this site's. |
| A program WordPress put in `wp-content/` or `var/` is found on the PATH: through `.`, an empty or a relative entry (each is whatever folder a command runs in), or an entry that is in the site folder, or leads into it through links, when the command looks it up. It would run as you, so it could read the Keychain item itself. | Every Offprint command starts `#!/bin/bash` and runs the tool's other scripts with `/bin/bash`, never a bash the PATH finds. Before anything is looked up on the PATH, it leaves out each entry that is empty, relative, or in the site folder or leads into it, says which in one line, and never leaves the PATH empty (`/usr/bin:/bin:/usr/sbin:/sbin` when nothing is left). The site folder is the one it is run in or below, or `OFFPRINT_SITE` (for `host-setup` and `host-undo`, also the folder named on their command line), and inside is asked of the disk. An entry `~` or `~/...` is your `HOME`'s, as bash takes it, when `HOME` is an absolute path with no colon in it; otherwise it is left out, and named. It also leaves out, without a word, each entry that can't be entered when it starts (not there, a link to nothing, a folder closed to you): it runs nothing then, and nothing made or opened there later can be reached through it. One that leads to a folder with a colon in its name (a Finder name with a `/` in it, say) is left out too, as a colon can't be written in a PATH, and named, with that reason. Each entry it keeps is kept as the folder it leads to then, on disk, not as its name; so is `TMPDIR`, which is refused when it is in the site folder or can't be entered. So a link on the way that WordPress points elsewhere later changes nothing. As a second layer, set-up, doctor and a publish never run a node, npm or wrangler in the site folder, nor hand the token to a curl or Cloudflare's answer to a php there. Not stopped: an absolute entry outside the site folder (another site's `wp-content/`, say) is yours to keep clean, as for any command. And at the moment of the check, a link in a folder WordPress can write, on the way of an entry or of `TMPDIR`, can make it lead to any folder outside the site folder that is there at that moment, another site's folders (its `wp-content/`, say) included: a PATH or `TMPDIR` that passes through the site folder is your choice. |
| A stranger's comment carries script, or a link chosen to break the site: one to `wp-admin`, or to a page of this site that isn't there, which would fail every publish once the comment was approved. | A comment is opened and checked on the Mac, outside WordPress, and reaches WordPress only through the import: every comment is held for you, WordPress's HTML filter is turned on (under WP-CLI it is off by itself) and the import refuses to go on without it, a link, a quotation's source and the commenter's own address keep an address only when it is a whole `http(s)` one to another site, and an address of this site's own in a comment's words (which WordPress would turn into a link when it shows it) is replaced with "[a link to this site]". However the host name is written (a letter as a character reference, percent-encoded, fullwidth), it is no link: the import makes a link of each bare address itself, as WordPress would, and keeps only one that is plainly another site's, and the exported page links nothing more in a comment that came this way. Not stopped: a plugin in your WordPress, which is handed every imported comment as WordPress takes it, and can read it afterwards; one that sends new comments to a service of its own sends these too. |
| A page's comment form names other keys than yours, or another path: WordPress prints both, from values it took when its container was made (so a container made before `site.json` changed still prints the old ones). Or the script that encrypts a comment is not the tool's: it is served from the plugin copy WordPress can write. | `bin/check-site` compares every page's block with `site.json`'s own path and keys, and refuses either script unless it is byte for byte the tool's own. Not stopped: a plugin in your WordPress that puts a script of its own on a page can read what a visitor types there, whatever the block says. |
| A visitor's browser doesn't run the script (scripts off, the script not loaded, a press before it had), and the comment form posts their name, email address and words readable. | The form is printed unable to post: its method is `dialog`, which a browser does nothing with, so without the script nothing is sent at all. `bin/check-site` refuses a page whose comment form is anything else, and any other form or button on a page that would send to the pigeonhole's path, however its address is written. |
| The page or the script a visitor is handed is changed on its way to them, by the host or a proxy in front of it: other keys, another script, or one more script that reads a comment as it is typed; and every comment from then on is read by whoever did it. | Not stopped: whoever serves the site can do this, and the checks before a publish cannot see it. Seen, when it lasts: once the live site serves a publish, the publish fetches one page with a comment form and the two scripts as a visitor would, gives them the check an export gets, compares the scripts the live page runs with the published page's, and warns loudly ("Action needed:", and the admin bar turns red) when anything differs, or when the live site answers one of them with an error or far too much. It is a tripwire, not a proof: one page is asked for, the request can be told from a visitor's, and the bytes of the page's other script files are not read. |
| The store's machine is broken into. | It holds ciphertext only the owner's keys open, when each arrived, and nothing else: no address is written down. It can drop or add submissions. It is reached by the web server alone (its firewall, and its unit's own limit on who it may speak with), runs as a user of its own that can write its store and nothing else, and never starts a connection. Not stopped: someone there who also takes a copy of the Mac's daily key reads what they kept. |
| The web server is broken into. | Nothing already sent is readable there: it passes ciphertext on and keeps none. From then on it can do what the row above says of a host. The user the Mac's ssh passes through has no shell, and its key may only open a connection to the store's ssh. |
| The pull key is copied from the Mac. | It fetches ciphertext, which it can't open, and can remove submissions not yet fetched. It gets no shell on either server: on the web server it may only open a connection to the store's ssh, and may listen on nothing (its key's line, and an sshd rule for that user); on the store it may only run the pull command (list, get, delete, by names of 64 hex digits), and only when it comes from the web server's address. Each server's line for it is root's, not the user's. On the Mac it is in the login Keychain, goes to a run's own `ssh-agent` on a pipe, and is never in a file, a variable or an argument. |
| A machine answers in a server's place (an address taken over, a rebuilt machine, something on the path). | Both machines' ssh host keys are pinned in `site.json`. A fetch writes them into a `known_hosts` of its own and never learns a key: a machine that shows another is not spoken to, and the message says which. Nothing of your own ssh set-up is read or changed. |
| The store answers the Mac with something other than what was sent: a file that is not its name's, a huge one, names that reach outside the spool. | A name is matched (64 hex digits and `.age`) before it is used, and one line that is not a name means nothing is fetched. No more of a file is read than a submission can be. A file is kept only when its bytes hash to its name, and is otherwise left on the store and counted. A file is removed from the store only once the Mac holds it whole. Each ssh is cut off after a minute and a fetch after ten, and what ssh says of a failure is capped, so a server can't keep the Mac waiting or fill its disk; what it says is never shown, and can't point you at the other machine. Not stopped: a store that has been broken into can hand the Mac well-named junk, 500 files a fetch, which waits in the spool until you collect and is then refused. |
| A visitor floods the store, or sends a body a byte at a time to hold its few places. | The store takes 10 an hour from one address and 300 from everyone, refuses anything that is not a submission's exact size or lacks a proof of work, and holds 5000 at most. The printed Caddy lines take the whole of a request before passing any on, cap its size, and set the visitor's address themselves in place of anything the visitor sent (the store refuses a request with none). That address is used for the limit, held in memory, and never written down. Not stopped: with a proxy in front of the web server and its trusted proxies not set, every visitor shares the proxy's address and its limit. |
| WordPress asks for comments to be opened: anything in it can press "Check for comments". | It can cause a collection, which hands it comments it would be handed anyway. It can't read a key or anything unopened: the spool and both keys are outside every folder it can reach. The scheduled fetch never reads the daily key. What the Mac tells it (the admin bar's counts, the notification) is numbers, times and one fixed word, never a comment's text. |
| A page or stylesheet is written in UTF-16 or UTF-32: a browser reads it, and the checks, which read bytes, see no link, host name or form in it. | Refused by the mark at its start: WordPress writes UTF-8. (A feed or sitemap is read by the XML parser in its own encoding, and checked.) |

Each of these exists because a review broke the version before it.
